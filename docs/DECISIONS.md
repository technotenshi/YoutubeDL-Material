## 2026-10-31 Tag releases with fork-owned SemVer

- Format: the git tag is `vMAJOR.MINOR.PATCH` for stable releases and `vMAJOR.MINOR.PATCH-alpha.N`, `-beta.N` or `-rc.N` for pre-releases. The pre-release identifier ends in a dot and a number so tools order it correctly. The numbering belongs to the fork and starts at 1.0.0. It does not continue Upstream's 4.x line, because a future Upstream `v4.4.0` would then mean something else. The existing `v1.0.0-alpha` (on `dda7143`) is valid SemVer and stays; the next pre-release is `v1.0.0-alpha.1`.
- The Upstream version is not encoded in the tag. Build metadata (`+...`) is ignored when SemVer compares versions and Docker tags cannot contain `+`. Each release's notes say which Upstream commit the release is based on instead.
- What the version promises is the contract of the running image: environment variables and config keys, volume paths, port, UID and GID, the database layout and its migrations, and `Public API v1.yaml`.
  - MAJOR: a break in that contract, for example a removed or renamed env var or config key, a changed volume path, port or UID/GID, a database migration with no way back, or a break in the API schema.
  - MINOR: a new feature, an Upstream sync that brings features, or a runtime base change that keeps the contract (Ubuntu, Python or Node).
  - PATCH: a fix, a security or dependency update, or an Upstream sync that only brings fixes.
  - Docs-only and CI-only changes do not get a release.
- Docker tags, for when #21 turns publishing on (the `docker-release.yml` job is still guarded to Upstream): a stable tag `v1.2.3` gives `1.2.3`, `1.2`, `1` and `latest`. A pre-release tag gives only its full version, for example `1.0.0-alpha.1`, and never `latest`, `1.0` or `1`. `nightly` and `sha-<short>` stay as in #19. This supersedes the wording of #21 for pre-releases: #21 says every published release gets a version tag plus `latest`, and for a pre-release this entry applies instead (stable releases are unchanged). The text of #21 itself is not edited here. This is how `docker/metadata-action` handles `type=semver`; it is read from the action's README, not run here.
- Release steps: check that CI is green on `main`; create an annotated tag with `git tag -a vX.Y.Z -m "..."` on `main` and push it; `build.yml` builds on the tag and creates a draft release with the zip, so do not create a second release by hand; edit the notes, tick "pre-release" for any version with a hyphen, and publish.
- `CURRENT_VERSION` in `backend/consts.js` (`v4.3.2`), the root `package.json` version (4.3.2) and the backend `package.json` version (1.0.0) are not changed by a release for now. The in-app updater compares `CURRENT_VERSION` with Upstream's latest release tag as strings, so setting it to a 1.x value would make the app offer Upstream's `v4.3.2`, and installing that overwrites fork files (#17). Revisit when #17 is decided. Until then the tag and the version the app prints differ.
- Found while checking, not fixed here: `build.yml` always creates the draft release with `prerelease: false`, so pre-releases need the box ticked by hand; and `v1.0.0-alpha` has two releases on one tag, a published pre-release with no assets (created by hand) and a draft with `youtubedl-material-v1.0.0-alpha.zip` (created by `build.yml`).
- Not verified: no release was cut, the Docker tag behavior was not run, and the release steps were not exercised. No tag, release or workflow was changed.
